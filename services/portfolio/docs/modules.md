# portfolio domain modules

The "three-file shape of a domain module" section of [`architecture.md`](architecture.md), moved here verbatim to keep
that file under the repo's 64KB limit (RK-8). Its pointers to sections that stayed behind now
link back to it. Every domain module's shape, and why it deviates from the three-file default
(`base.py` + `*_source.py` + `repository.py`, as
[data-store's](../../data-store/docs/architecture.md) defines it), is here; the layering it sits in is
[`architecture.md`](architecture.md)'s.

## The three-file shape of a domain module

| Module | Shape | Deviation from the three-file default, and why |
|---|---|---|
| `accounts/` | `repository.py` only | No external source and no `base.py` — a broker and an account are user-declared reference data, created through a CLI command, not parsed or fetched. Every read here takes a `user_id`, and every other domain module's queries are reached only by first going through an account scoped to that user — this is the one place multi-user isolation is enforced, not repeated independently by each module. **Deliberately no unscoped `get_by_id(account_id)`** alongside `get_by_label` — that absence is the design, not an oversight: it removes the one shortcut that would let a caller reach an account without proving it owns it. |
| `broker_import/` | `base.py` (the `BrokerParser` and `CashflowParser` Protocols) + `discovery.py` (entry-point lookup, populating `pipeline.py`'s two registries) | **No `repository.py`.** A parser hands back in-memory `CanonicalTransaction` records; persistence is owned entirely by `transactions/repository.py`, so a manually-entered transaction and an imported one are written through the exact same path. Splitting persistence into `broker_import/` would let the two paths drift. **No concrete implementation lives in this module at all** — every `BrokerParser`/`CashflowParser` is an entry-point plugin from a separately-installed package; `discovery.py` is the only file here `pipeline.py` imports directly, and it never imports a concrete parser either. |
| `ticker_mapping/` | `base.py` (the `TickerMappings` lookup) + `repository.py` | `base.py` holds the in-memory lookup every rebuild resolves through, `resolve(kind, identifier, broker)`; `repository.py` persists the global `ticker_mappings` table and loads it into that lookup once per run (`load_all`), so a rebuild resolves every row against one consistent set rather than querying per row. No `*_source.py` — mappings are entered by an admin, not fetched. Until the admin page existed this was a YAML file and `loader.py`; see the cross-cutting decision on ticker-mapping storage. |
| `transactions/` | `base.py` (the `CanonicalTransaction` record shape) + `repository.py` | `base.py` here holds a **data shape**, not a `Protocol` — the contract is "what a normalized transaction looks like," which multiple producers (`broker_import` parsers, manual CLI entry) must fill in, not a swappable behavior one class implements. |
| `positions/` | `calculator.py` (pure) + `repository.py` | **Built at task 7.** Same shape as data-store's `returns/`: no `base.py`, no `*_source.py` — the input is this service's own `transactions` and `ticker_mapping` tables, not an external provider. One deliberate deviation from "repositories never commit": `positions/repository.py` still never commits, but `pipeline.rebuild_positions` opens the `with transaction(conn):` boundary once *per `(account, canonical_ticker)` pair* rather than once per flow, because `schema.md`'s delete-then-insert contract requires each pair's replacement to be atomic on its own, not the whole rebuild run. |
| `returns/` | `calculator.py` (pure) + `performance.py` (pure) + `repository.py` | **Built at task 8.** Same shape again, plus one more thing to disclose: it also needs prices and FX rates from `datastore_client`. Those are fetched by `pipeline.py` and handed into `calculator.py` as plain data — the calculator itself stays pure and knows nothing about HTTP, keeping it as unit-testable as data-store's `returns/calculator.py`. A second thing to disclose, surfaced only once `return_snapshots`' original mark-to-market-only design turned out not to account for dividend income: `calculator.py` also takes a `DividendEvent` sequence per pair, needing no `datastore_client` call at all (`transactions.eur_amount` is already frozen in EUR) — but resolving which `DIVIDEND` transactions belong to which ticker is `pipeline.rebuild_returns`'s job, via the same `mappings.resolve` `rebuild_positions` already uses for `BUY`/`SELL`. `returns/` is therefore not quite as decoupled from `ticker_mapping/` as `position_snapshots` being pre-resolved might suggest. **`performance.py`**: pure. `compute_series` sums stored `return_snapshots` rows from every account a user holds into one series per priced day, keyed on (account, ticker) and forward-filled per pair, through `forward_filled`, the calendar walk `twr/calculator.py` shares (RK-10). It writes nothing; see "The portfolio series is summed here, on read" in [`architecture.md`](architecture.md). It once also computed time-weighted growth since inception (`GET /returns/growth`, plus `growth_pct`/`by_ticker` on `GET /returns/portfolio`); that was removed, see "Growth since inception was removed" in [`architecture.md`](architecture.md). |
| `holdings/` | `aggregator.py` (pure) + `flows.py` (orchestration) | **Built at PF-1, extended at PF-5.** No `repository.py` and no table of its own: it reads `positions/` and `returns/` latest rows through their repositories and sums them per ticker across a user's accounts, on read. PF-5's cross-account return series is orchestrated here too, with `returns/performance.py` as its pure part. `aggregator.py` is pure, like the calculators. `flows.py` is the orchestration around it, kept out of `pipeline.py` (see [`architecture.md`](architecture.md)'s Layering). Rows stay keyed on (account, ticker) until the final merge, so the same ticker in two accounts can't collapse into one account's row, the bug UI-11 documented in web's `aggregate_portfolio_returns`. See "Holdings across accounts are summed here, on read" in [`architecture.md`](architecture.md). |
| `labs/` | `calculator.py` (pure) + `risk.py` (pure) + `flows.py` (orchestration) | **Built at LB-3, extended at LB-4.** Backtests a mix of assets for Labs: each asset's and the buy-and-hold mix's % return in EUR over 1M to 5Y and Max, plus the daily growth series for one period. No `repository.py`: nothing is stored (saving labs is deferred), and the inputs are data-store's, not this service's tables. No `base.py`: the input is `datastore_client`'s own `PricePoint`/`FxPoint`, so the calculator imports those shapes from `datastore_client/base.py` (the same one-way dependency `returns/calculator.py` has) rather than defining look-alikes the endpoint would have to copy into. The caller picks each asset's FX series, so this module never maps a currency code (`TickerInfo.fx_currency` already did). The rules, including how a NULL return is bridged and why, are in the module docstring. **RK-5**: the EUR conversion itself moved to `eur_returns/`; the calculator chains that module's `r_local` into its levels and prices them with its `FxSeries`. **LB-9**: the mix holds only the assets that cover each period, re-weighted, and names the rest in `left_out`; Max is each asset's whole history, with the mix rebalanced to its target weights as each asset joins. `flows.py` (LB-4) fetches the inputs and gives every requested asset a status: included, not tracked, no history yet, no FX rate, or failed (see [`architecture.md`](architecture.md)'s Layering, "Labs orchestration"). `Period` is a `StrEnum`, so the API parses and writes `"1M"` to `"Max"` without a mapping of its own. **RK-8** added `risk.py`, the backtest's risk table: spec §5.1–5.5 over the spec's windows (1Y/3Y/5Y/10Y/Max, not Labs' periods) for the mix and each asset, and the mix's drawdown series for the chart period. It is in `labs/`, not `risk/`, because `risk/` imports nothing from portfolio and this is the code that turns Labs' series into the library's. Three agreed rules. **One common window for every row** (R10): Max starts on the youngest asset's first day, and any window starting earlier is uncovered on every row, naming that asset, so the table compares like with like; *rejected: each row over what it covers*. It also means every covered window holds every asset, so none of LB-9's re-weighting or Max's joins reach the risk path. **The mix drifts** (R3), re-based at each window's start, from the calculator's own per-asset EUR levels (`AssetSeries`, made public for this), weighted in numpy floats rather than Decimal for speed; a test pins its 1Y and 5Y returns to Labs' to 1e-8. Any asset's NULL makes the mix's day a gap (R5) while the levels stay bridged. **The drawdown chart is the mix's only**, measured on Labs' own growth line so it matches the chart above it, with breaks on gap dates. Each asset's row uses its own `r_eur` (spec stream 1). |
| `eur_returns/` | `calculator.py` (pure) + `fetch.py` (data-store fan-out) | **Built at RK-5** (tasks-risk-thread.md). An asset's daily EUR return series, `r_eur = (1 + r_local) × fx(t−1)/fx(t) − 1`, with `r_local` and `r_fx` beside it (risk spec §4.2). It exists so there is **one conversion**: Labs builds on it, and the risk path (RK-8 onward) takes its returns from it, so the two can't give different numbers (spec §4.2's CHECK). It was extracted from Labs' private `_Series` rather than written a second time beside it. Three choices to know about. **NULLs are kept**: a gap stays `None` in `r_local`/`r_eur`, because the risk path excludes gaps (spec R5), while Labs bridges them as flat days on its own side. **Decimal, not float**: the inputs are Decimal and Labs' figures are pinned to 8 places; the float risk library converts at its own boundary. **A reason code, not a message**: an ineligible asset is `NO_HISTORY` or `NO_FX_SERIES`, and the caller, which holds `TickerInfo.fx_currency`, words it ("no FX rate" in Labs, "no FX series for <CCY>" in risk); like `labs/`, the module never looks at a currency code. Labs keeps its levels-and-`FxSeries.on` form instead of chaining `r_eur`, because it prices every asset on the union calendar, where an FX move on a day the asset didn't trade has no `r_eur` of its own. On the asset's own dates the two forms agree, which a unit test pins. Same `datastore_client/base.py` input shapes and no `base.py`/`repository.py`, for `labs/`'s reasons. `returns/calculator.py`'s own on-or-before rate lookup converts market *values* for the cost-basis snapshots, not returns, and is left as it is. **RK-10** added `fetch.py`: the concurrent ticker-info, price and FX fetch that `labs/flows.py` used to hold, so the TWR and later risk flows fetch the same way (see [`architecture.md`](architecture.md)'s Layering, "Labs orchestration"). It returns a status code per ticker and neither words nor logs it. |
| `twr/` | `calculator.py` (pure) + `flows.py` (orchestration) | **Built at RK-10** (tasks-risk-thread.md). The whole portfolio's daily time-weighted return, invested positions only: risk spec stream 3, which ex-post risk (RK-11) is measured on. **Holdings-based**, as agreed on 2026-10-20: `r_t = Σ w_(i,t−1) · r_eur,i,t`, with each ticker's share of EUR market value at the previous date (from `return_snapshots`, summed across accounts) and its EUR total return from `eur_returns/`. *Rejected: flow-based* `(MV_t + D_t − F_t) / MV_(t−1) − 1`. `DIVIDEND` transactions are dated on payment while the market value is price-only, so each dividend would have to be matched to data-store's ex-date, a matching step with a fallback that can go wrong; the total return already carries the dividend on its ex-date. **What it gives up**: dividends count gross of withholding tax, fees and the gap between trade price and close are ignored, a position's first day counts from the next close, and its last day runs close to close. Those are small next to the risk figures' own sampling error. The cost-basis return on `GET /returns/portfolio` stays the figure for what was actually earned. **It is not the growth figure removed from the portfolio views** (see "Growth since inception was removed"). That one was flow-based and shown as performance; this one feeds risk and isn't shown in the portfolio views. Rules worth knowing before reading the code, each argued in the module docstring: the calendar is the union of the rows' dates; returns that fall between two calendar dates are compounded into the later one; a closed pair counts only through its last row, because a sale dated on a day with no price leaves that row's quantity above 0 and a forward-fill would keep its weight for good; a NULL on a held ticker makes the day a gap (spec R5); while nothing is held, there is no point at all, so an exit isn't a gap; a ticker without EUR returns is excluded, named, and the rest renormalised. It shares `returns/performance.forward_filled` with the portfolio series, so both walk the calendar the same way. Decimal, like `eur_returns/`. Served on `GET /returns/portfolio/twr`, its own route, so the existing chart endpoint's payload and its independence from data-store are unchanged. |
| `risk/` | pure library modules, no `flows.py` yet (Labs calls it from `labs/risk.py`) | **Built at RK-6** (tasks-risk-thread.md); the rules are in [`docs/domain/risk.md`](../../../docs/domain/risk.md). The foundations the risk measures build on: the return-series, window and `RiskFigure` types; weekly W-FRI aggregation; gap and suspect-row accounting; the §4.5 minimums; ACT/360 risk-free compounding; the VaR day mask. **No I/O and no imports from other portfolio modules**, not even `datastore_client`: callers convert to EUR (RK-5) and pass plain floats, so every spec golden test runs against the library alone. **Floats and numpy, not `Decimal`**: risk figures are statistical estimates with sampling error far above float rounding, and the later measures need quantiles and matrix maths. Money stays `Decimal`. Three agreed rules worth knowing before reading the code, each argued in its module docstring: partial weeks at a series' edges are dropped, so every week is Friday to Friday and assets line up; `has_suspect_rows` is any return above 100%, because data-store nulls every other such row; and the VaR mask counts a day as traded when data-store has a row for it. **Known limitation of that last rule:** data-store keeps rows for some zero-volume holidays, so one can pass the mask. The fix is to expose `volume` on data-store's price endpoint (RK-31). **Built at RK-7**: the §5.1–5.5 measures on one series, in **two layers**. `measures.py`, `drawdown.py` and `tail.py` are the maths at any frequency, with q a parameter and no minimums or flags; `single_series.py` is the layer callers use, and it turns their numbers into `RiskFigure`s. The split exists because §4.3's frequency rule and §5.7's golden test pull opposite ways: the layer refuses a daily series for volatility, Sharpe and Sortino (and a weekly one for return, drawdown and VaR), so no caller can pick the wrong frequency, while the golden test pins daily data at q = 252 on 7 points, under every minimum, and can only run against the maths. Choices to know. **Weekly windows shrink to whole weeks** (`weekly.weekly_window`), because RK-6 drops partial weeks, so a daily window's end is usually after the weekly series' last Friday; the figure reports the shrunk window, and risk-free returns run Friday to Friday, the span each weekly return covers. **An undefined ratio** (no variation, no return below rf, no drawdown) is greyed with a reason, never inf or 0; "no variation" is tested as identical values, not a zero stdev, which floats can miss. **VaR uses numpy's `linear` quantile** (Hyndman–Fan type 7, as R and Excel's PERCENTILE.INC), and CVaR averages the returns at or below it. **`nonsync_daily` is the caller's to set**: the library doesn't know which markets a series mixes. **The Sharpe's standard error** rides on its `RiskFigure` (`standard_error`), so one object carries "0.86 ± 0.59". A greyed drawdown still returns its DD series, so a chart can cover a period too short for the figure. **Built at RK-15**: ex-ante risk of today's mix (spec §6.2–6.3), in the same two layers. `covariance.py` is the maths (Σ, σ_p, MCR/CR/PCR, correlation with the portfolio, diversification ratio, effective N), where §6.3's golden test runs; `ex_ante.py` is the layer callers use. Between them, `listwise.py` builds R12's panel: only weeks on which every holding has a return. **R13 is held by type**: `ex_ante.py` accepts a `ListwiseReturns`, never a bare matrix, so a pairwise correlation matrix (RK-16), which needn't be positive semi-definite, can't reach portfolio maths. Two agreed rules. **A late holding shortens the window** (R12 as written) rather than greying it, and `limited_by` names it, so the UI can offer to exclude it. **σ_p greys at 52 weeks, the decomposition at 104**: σ_p equals the constant-weight weekly volatility exactly (§6.2's check, a test), so it takes volatility's minimum, or the page would grey one and show the other; the per-holding figures and the diversification ratio rest on correlations and take covariance's. *Rejected: 104 for all.* "Today's mix" through history is `constant_weight_series`, fed to the RK-7 layer rather than measured anew: on its daily union calendar a holding with no row is a closed exchange at 0% (R7, masked out of VaR by `var_days`), and any NULL makes the period a gap (R5). **Built at RK-16**: `correlation.py`, Pearson on weekly returns in R13's two forms. **Pairwise** (`PairwiseCorrelation`) is for display: each cell is a `RiskFigure` over the weeks that pair shares inside the window, with its own `n_obs` and start, so a late-starting asset still gets cells instead of shortening everyone's window. **Listwise** (`listwise_correlation`) is for maths and takes RK-15's `ListwiseReturns`, so the listwise ρ and Σ always come from the same weeks and R12 has one implementation. The separation holds as `ex_ante.py`'s does, by construction plus a runtime check, since portfolio runs no type checker: `PairwiseCorrelation` exposes cells (`cell(a, b)`), never an array, and `listwise_correlation` raises `TypeError` on anything but a `ListwiseReturns`. The library doesn't know about currency: the caller passes weekly series from RK-5's `r_eur` or `r_local` and labels which (RK-17). Clustering order (§7.1, optional) is left for RK-18's heatmap. **RK-8** is the first caller, through `labs/risk.py`, and added `single_series.weekly_figures_without_rf`: with no risk-free series (none stored, or a failed fetch) volatility stands and downside deviation, Sharpe and Sortino are greyed with the caller's reason, never computed against rf = 0. The library's own orchestration (`risk/flows.py`, with logging) arrives with its first endpoint of its own (RK-11, RK-17). |
| `datastore_client/` | `base.py` (a `DataStoreClient` Protocol) + `http_client.py` | This is the `*_source.py` role, but the "provider" is another in-house service's read API rather than a third party. **`get_fx_rate` built at task 14**, pulled forward from its original task 8 slot because a cash-ledger import needed it. **`get_price_series`, `get_fx_rate_series`, and `get_ticker_info` built at task 8** — see [`flows.md`](flows.md)'s "Cross-service prerequisite". `get_fx_rate_series` is a range-returning sibling of `get_fx_rate`, not a replacement: `returns/calculator.py` needs a whole date range's rates per `(account, ticker)` pair, and repeating a single-date `get_fx_rate` call per priced day would cost one HTTP round trip per day instead of one per pair; `get_fx_rate` itself is untouched and still serves `import_cashflow`'s single-date lookup. **`lookup_ticker` and `add_`/`list_`/`update_tracked_ticker` built at TK-7** (ticker onboarding): pure pass-throughs that share one `_tracked_request`, mapping `data-store`'s meaningful refusals to `TickerRequestRefused` and anything else to `DataStoreApiError`. **LB-2** (labs): `PricePoint` also carries `simple_return` and `TickerInfo` carries `currency`/`fx_currency`, so a backtest can chain data-store's total returns and pick each asset's FX pair; no new method. `simple_return` keeps NULL as `None` (a gap, never 0), and a missing key is a `DataStoreApiError` rather than a silent gap; a missing currency is `None`, since it can only leave an asset without an FX pair, never yield a wrong figure. **LB-4**: `get_ticker_info` and `get_price_series` quote the ticker as one path segment, as the tracked-ticker methods already did, because Labs passes them tickers a user typed rather than ones read from stored positions. **RK-4**: `get_risk_free_series` reads data-store's spliced €STR/EONIA series as `Decimal` points, unfilled. It returns `None` when nothing is stored, so "no risk-free data" can't be read as rf = 0. `risk/` keeps its own float `RatePoint` so it imports nothing from here, and the risk flows convert. |

**`errors.py` is not a domain module** — it's a single Foundation-layer file (`PortfolioError` plus
`InvalidBroker`, `AccountNotFound`, `AccountLabelConflict`, `InvalidTransaction`, and, as of task 6,
`BrokerFileError`, `TickerMappingError`, plus `BrokerParserNotFound` and `BrokerPluginError` from
the broker-plugin extraction, `DataStoreApiError` from task 14, and `UnknownTicker`,
`InvalidTickerMapping` and `TickerMappingNotFound` from manual ticker entry and the admin mapping
page), not one per module, so every
domain-level failure `pipeline.py` or a pure validator raises shares one parent. Repositories
never raise these — they let the driver's own exceptions (e.g. `psycopg.errors.UniqueViolation`)
propagate uncaught, same as `auth`. **`jobs.py` itself no longer catches `PortfolioError`** — see
[`flows.md`](flows.md)'s "HTTP API" for why that changed at task 9 and what each entry point does with it instead.

**Revised — `--broker` dropped from `import-transactions`/`import-cashflow`, and `BrokerMismatch`
removed with it.** The original design took `--broker` as an explicit argument on both commands
and raised `BrokerMismatch` if it disagreed with the resolved account's own `broker` column — but
that column is *always* available once `--account` resolves (`AccountNotFound` fires first if it
doesn't), which made `--broker` pure input to re-validate against data the system already had.
Both flows now look the parser up from `account.broker` directly, which removes `BrokerMismatch`
as an error class entirely (nothing is left that can disagree with itself) and one CLI flag users
had to get right on every import.

**One cross-domain dependency worth disclosing up front**, in the spirit of data-store's disclosed
deviations: `broker_import/base.py`'s `BrokerParser.parse()` and `CashflowParser.parse()` both
return `list[CanonicalTransaction]`, so `broker_import` imports the record shape from
`transactions/base.py` — and so, transitively, does any installed plugin implementing either
Protocol. That's the one place a domain module reaches into another domain's module rather than
staying self-contained — accepted because the alternative (each parser inventing its own
intermediate shape, reconciled later) is exactly the drift the extension point exists to prevent.
