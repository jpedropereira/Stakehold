# web endpoint surface

The route table of [`architecture.md`](architecture.md), split out for size: every route `web`
serves, what it requires and which upstream calls it makes. It's part of that document, so
`.claude/rules/architecture.md` applies to it too: adding, removing or changing a route updates
this file in the same change. The reasoning behind a route lives in `architecture.md`'s "Key
decisions", or in [`ui-architecture.md`](ui-architecture.md) for how its page looks and behaves.

| Route | Behaviour |
|---|---|
| `GET /` | `require_user` dependency (no valid session → redirected to `/login`, an `AuthRequired` exception mapped to a 303 by an app-level handler); the nav's "Overview" (UI-11, `api/overview.py`). Fetches `portfolio`'s `GET /accounts`, then `GET /returns/latest` per account concurrently, and renders a "Prices as of" line, the same four tiles as `GET /portfolio` totalled across accounts, and one row per account (label linking to its holdings, broker, market value, total return € and %). A row whose call failed says so and is left out of the totals, with a notice; an account with no return row yet is "Waiting for prices". No accounts → a first-run card linking to `/accounts`; a failed account list → a notice, never the first-run card (see "Key decisions" in [`architecture.md`](architecture.md)) |
| `GET /admin` | `require_admin` dependency: an admin → the admin page (a link to ticker mappings), linked from the nav only for admins; a logged-in non-admin → a 403 page (`AdminRequired`, mapped by an app-level handler); no valid session → redirected to `/login`, like every `require_user` route |
| `GET /admin/mappings` | `require_admin`; fetches `portfolio`'s `GET /ticker-mappings`, `GET /instruments/unmapped/all` and `GET /instruments/tickers`, and renders three things: the instruments still waiting for a mapping (each with an inline "map to ticker" form), the existing mappings (each with a delete button), and a form to add or re-point one. Each list degrades on its own to a notice rather than an empty table, so an outage never reads as "nothing to map". After a save or delete, the redirect's query string (`saved`/`deleted`, `rebuilt`, `failed`) drives a one-line outcome banner |
| `POST /admin/mappings` | `require_admin`, CSRF-checked; calls `portfolio`'s `PUT /ticker-mappings` with the admin's own `user_id` as `updated_by` (a blank broker is sent as `null`, which an ISIN needs; portfolio enforces which kind needs one and its 422 message is shown as-is). Redirects to `/admin/mappings?saved=1&rebuilt=<n>&failed=<m>` |
| `GET /tickers` | `require_user`; ticker onboarding (TK-8, `api/tickers.py`). Lists `portfolio`'s `GET /instruments/tracked-tickers`, narrowed to `requested_by=<user>` for a user and unfiltered for an admin, with each ticker's status as a neutral badge (Queued, Loading, Ready, Couldn't load). An admin also sees each one's source (default list or a user) and its last error, with Retry for a failed ticker and Disable/Enable for a user-added one; a default-list ticker is turned on and off in `tracked_tickers.yaml`, so it gets no such control. A failed list call shows a notice, never "none added". `added`, `already` or `changed`+`change` in the query string drive the outcome banner, and only a ticker-shaped value is echoed |
| `GET /tickers/new` | `require_user`. A GET lookup form (`symbol`): a lookup changes nothing, works without JS, and can be bookmarked. With a symbol, it calls `GET /instruments/tickers/{t}/lookup` and shows what adding would do: for an `available` symbol, its name, exchange and currency plus an "Add" confirmation; otherwise where it already stands (`tracked`) or why it can't be added (`unsupported`, `not_found`, `unavailable`). A symbol quoted in minor units (`GBp`, `ZAc`, `ILA`) carries a warning that its values will read 100 times too high, the known limitation in `tasks.md` |
| `POST /tickers` | `require_user`, CSRF-checked; calls `POST /instruments/tracked-tickers` with the user's id and `enforce_limit = not user.is_admin`. This is the one place web decides who skips the daily limit. Redirects to `/tickers?added=<t>` or `?already=<t>`. Each refusal re-renders the add page with its own sentence: not on Yahoo (404), can't be added (422), daily limit reached (429), Yahoo didn't answer (503) |
| `POST /tickers/{ticker}/{retry,disable,enable}` | `require_admin`, CSRF-checked; calls `PATCH /instruments/tracked-tickers/{t}`. POST because a plain form can't send PATCH. A 404 or 409 (a default-list ticker's on/off, or retrying one that hasn't failed) re-renders the list with the reason |
| `POST /admin/mappings/{id}/delete` | `require_admin`, CSRF-checked; calls `DELETE /ticker-mappings/{id}`. POST rather than DELETE because a plain HTML form can't send DELETE and the page has no script. An already-deleted mapping (portfolio's 404, mapped to `TickerMappingNotFound` on this route only) re-renders with "That mapping was already deleted." |
| `GET /login`, `GET /signup` | `optional_user` dependency: already logged in → redirected to `/`; otherwise renders the form with a fresh or existing CSRF cookie |
| `POST /login`, `POST /signup` | CSRF-checked, calls `auth`, proxies the `Set-Cookie` `auth` returned, then redirects to `/` — a 303 for a plain form post, or an `HX-Redirect` response header for an `hx-post` (htmx's own XHR follows a 303 by swapping the *content* of the request's own response into the target element, which would drop a full HTML document into a form's error slot; `HX-Redirect` instead triggers a real browser navigation) |
| `POST /theme` | No login needed. CSRF-checked: a mismatch changes nothing and redirects back (an `HX-Redirect` for htmx), like `POST /logout`, rather than re-rendering a form error. A value other than `light`/`dark`/`system` → `400`. Otherwise sets the `stakehold_theme` cookie (`HttpOnly`, `SameSite=Lax`, `Path=/`, one year, `Secure` per `WEB_COOKIE_SECURE`), then a 303 to the validated `next`, or for htmx a `200` with `HX-Trigger`. See "Theme" in [`ui-architecture.md`](ui-architecture.md) |
| `POST /logout` | CSRF-checked, calls `auth` (best-effort — a failure is logged, not surfaced, since the user's intent to log out should not depend on `auth` being reachable), clears the session cookie locally, redirects to `/login` |
| `GET /glossary` | `require_user`; `api/glossary.py`. Static: what each holdings figure means, one anchored entry per term, linked from the holdings pages' headers and tiles. Calls no upstream service. See "Glossary" in [`ui-architecture.md`](ui-architecture.md) |
| `GET /health` | `200 {"status": "ok"}`, unauthenticated, no dependency check (see "Key decisions" in [`architecture.md`](architecture.md)) |
| `GET /accounts` | `require_user`; lists the caller's accounts (`portfolio`'s `GET /accounts`) and installed brokers (`GET /brokers`) and renders them as a list (the name links to holdings; Transactions / Add / Import beside it, and a Delete link; see `GET /accounts/delete`), with the create-account form in a `<details>` below it, open on first run or after a create error (see [`ui-architecture.md`](ui-architecture.md)). Its broker field is a `<select>` of those brokers plus "Custom". A failed list shows a notice above the list, never the first-run steps. Each account's transactions are counted for its Delete warning (`transaction_counts.py`: `GET /transactions` per account, concurrently, as `portfolio` has no count endpoint); a count that fails reads "every transaction in it", never zero. After a delete, `?deleted=1&transactions=<n>` shows "Account deleted." and how many transactions went with it, and `?deleted=0` says the account was already gone. The label isn't put in the query string, so a crafted link can't put words in the banner |
| `POST /accounts` | CSRF-checked. With "Custom" chosen (`broker=__custom__`), sends the typed `custom_broker` name instead, after refusing a blank one or one matching an installed broker ignoring case (both 422, no `portfolio` write). Calls `portfolio`'s `POST /accounts`, redirects to `/accounts` on success |
| `GET /transactions/new` | `require_user`; required `account` query param (a bare 422 for a missing/blank value — reachable only via a hand-crafted URL, since every link that points here already includes it); renders the manual-entry form, with a confirmation banner if `?saved=<n>` (plus the rebuild outcome from `positions`/`returns`; see "Key decisions" in [`architecture.md`](architecture.md)). Fields are grouped into What / When / Amount / Instrument fieldsets; the reference is prefilled with a fresh `manual-<uuid4>`, the date with now (UTC) and the currency with EUR (a datalist suggests others), and `transaction_form.js` hides the fields the chosen type doesn't use (see [`ui-architecture.md`](ui-architecture.md)). The instrument field is a ticker picker: a native `<datalist>` filled from `portfolio`'s `GET /instruments/tickers` (no script, so the strict CSP is untouched). If that call fails, the form still renders with an empty list and a notice; the picker is a convenience, and portfolio checks whatever is typed when it's saved. Also fetches `GET /accounts` (concurrently) for the account header: a label that isn't one of the visitor's accounts renders `account_not_found.html` with a 404, and a failed fetch degrades to a label-only header rather than a 404 |
| `POST /transactions/new` | CSRF-checked, calls `portfolio`'s `POST /transactions` (an instrument, when given, is always sent as `instrument_identifier_kind = 'TICKER'`; a blank Amount is sent as `null`, for portfolio to derive on a BUY/SELL or reject as missing on anything else), redirects to `/transactions/new?account=<label>&saved=<transactions_saved>&positions=<status>&returns=<status>` on success. An unknown ticker comes back as portfolio's 422, whose message is shown as-is like every other 422. The ticker list is re-fetched for the error re-render |
| `GET /transactions/import` | `require_user`; required `account` query param; renders the upload form with an importer `<select>` listing the account's own broker's importers and the file input styled as a drop zone, with the 20 MB limit stated. With `?imported=<n>` it adds an import summary (count and rebuild outcome) and links to the account's holdings and transactions, with the form below as "Import another file". A broker with no importer gets a pointer to manual entry instead of a form; brokers that can't be listed get an inline notice, never the "no importer" text. Fetches `GET /accounts` (for the account header, with the same 404 and degrade rules as `GET /transactions/new`) and `GET /brokers` concurrently |
| `POST /transactions/import` | CSRF-checked, multipart; `importer` must be `transactions` or `cashflow` (anything else is a 422 with no `portfolio` call); size-capped at 20MB (matching `portfolio`'s own cap) before the bytes are forwarded; calls `portfolio`'s `POST /transactions/import` or `POST /cashflows/import` to match, redirects to `/transactions/import?account=<label>&imported=<rows_saved>&positions=<status>&returns=<status>` on success |
| `GET /transactions` | `require_user`; required `account` query param; fetches `portfolio`'s `GET /transactions` and `GET /accounts` (for the account header) concurrently, and renders the log newest first (reversed in `web`; see "Key decisions" in [`architecture.md`](architecture.md)): date, type badge, instrument, quantity, price, amount (with the EUR amount under it on a non-EUR row), fees, reference, and a Delete link (see `GET /transactions/delete`). No pagination. An empty log shows links to Add and Import. After a delete, `?deleted=1` (plus the rebuild statuses) shows "Transaction deleted." with the rebuild outcome, and `?deleted=0` says nothing was deleted because the row was already gone. `AccountNotFound`, or a label missing from a successfully loaded account list, renders `account_not_found.html` with a 404; any other failure renders a banner and no table, never the empty state; a failed account list degrades to a label-only header |
| `GET /accounts/delete` | `require_user`; required `account` query param. The no-JS confirmation page an account's Delete link points to (`api/deletion.py`): "This deletes ‹label› and its N transactions.", a "can't be undone" warning, and a form posting to `POST /accounts/delete`. Fetches `GET /accounts` (for the header) and the account's `GET /transactions` (for the count) concurrently. An unknown account is a 404. A failed count still offers the delete, with the vague wording: unlike the transaction delete, what goes is already known (the whole account). With JS, the accounts list opens the same confirmation as a dialog instead |
| `POST /accounts/delete` | `require_user`, CSRF-checked; posted by both the dialog and the page. Calls `portfolio`'s `DELETE /accounts` with the visitor's own `user_id`, which removes the account and everything recorded in it, then redirects to `/accounts?deleted=1&transactions=<transactions_deleted>`. Nothing is rebuilt afterwards, so there are no rebuild statuses. A 404 (`AccountNotFound`) redirects with `deleted=0`; any other failure, a CSRF mismatch included, re-renders the confirmation page with the error |
| `GET /transactions/delete` | `require_user`; required `account` and `ref` query params (`ref` is the row's `broker_transaction_ref`, which with the account is what identifies a transaction to `portfolio`). The no-JS confirmation page each Delete link on the log points to (`api/deletion.py`): the transaction's date, type, instrument, amount and reference, a "can't be undone" warning, and a form posting to `POST /transactions/delete`. `portfolio` has no single-transaction read, so the account's log is fetched (with `GET /accounts` for the header, concurrently) and searched. An unknown account is a 404 like the log's; a row that's gone redirects to the log with `deleted=0`; a failed fetch shows a notice and no form, since the visitor would be confirming a delete they can't see. With JS, `confirm_dialog.js` opens the same confirmation as a dialog on the log instead (see [`ui-architecture.md`](ui-architecture.md)) |
| `POST /transactions/delete` | `require_user`, CSRF-checked; posted by both the dialog and the page. Calls `portfolio`'s `DELETE /transactions` with the visitor's own `user_id`, then redirects to `/transactions?account=<label>&deleted=1&positions=<status>&returns=<status>`. POST rather than DELETE because a plain HTML form can't send DELETE. A 404 (the account or the row is gone; `TransactionNotFound`) redirects with `deleted=0` rather than showing an error: the visitor wanted the row gone. Any other failure, a CSRF mismatch included, re-renders the confirmation page with the error, so a delete started from the dialog can be retried from there |
| `GET /accounts/holdings` | `require_user`; required `account` query param; fetches `portfolio`'s `GET /positions`, `GET /returns`, `GET /returns/latest` and `GET /instruments/unmapped` concurrently. Renders a "Prices as of" line and summary tiles (market value, cost basis, total return € and %, dividends; `portfolio_view.summarize_latest_returns`), a holdings table of open positions joined to their latest return row (quantity, average cost, market value, weight, unrealized return; `portfolio_view.build_holdings`), and a Chart.js chart of the per-ticker series aggregated into one portfolio-level series (`portfolio_view.aggregate_portfolio_returns`, `portfolio_view.build_chart_payload`), with a total return / market value toggle and date ranges. `GET /accounts` is fetched concurrently for the account header. `AccountNotFound` on any call, or a label missing from a successfully loaded account list, renders `account_not_found.html` with a 404; any other failure degrades only the part that call feeds, mirroring `GET /accounts`'s own pattern. Pending states: "Waiting for prices" on a holding with no return row, and a notice listing the instruments waiting for a ticker mapping at this account's broker (UI-7). No writes, no rebuild trigger. |
| `GET /portfolio` | `api/portfolio.py`. With `account`: no auth, a 308 to `/accounts/holdings` with the query string passed on unchanged (PF-2); an empty `account` is the branded 422. Without it: the login check, then the nav's "Portfolio" (PF-4), every holding summed across accounts from `portfolio`'s `GET /holdings`, with tiles from its totals, a per-account breakdown per row, and the user's unmapped instruments; and (PF-6) from `GET /returns/portfolio`, the per-account page's chart (see "Key decisions" in [`architecture.md`](architecture.md)) |
| `GET /labs` | `require_user`; `api/labs.py` (LB-6). Backtests the user's current holdings: `portfolio`'s `GET /holdings`, then `POST /labs/backtest` with the default mix from `labs_view.build_default_mix` (priced holdings weighted by market value, largest first, at most 50; unpriced, zero-value and over-cap holdings are named in notes, not sent). The calls are sequential, since the second needs the first. A failed holdings call shows a notice and runs no backtest; a failed backtest shows a notice above the notes, and a 422 shows `portfolio`'s own message. No holding with a market value → "Nothing to backtest yet" and no backtest call. `?period=` (`1M` … `Max`, exactly as `portfolio` spells them; 1Y when absent or anything else, logged) picks the growth series the chart draws (LB-8); the period links keep the rest of the query string. LB-7: the query string can carry an edited mix instead, as repeated `ticker`/`weight` pairs (weights in %), with `last_ticker`/`last_weight` for the mix the table showed (`labs_mix.py` has the contract). An edited mix makes no holdings call. It is checked against `GET /instruments/tickers` (fetched for the form's suggestions in either case), and is sent only if every row is valid; otherwise the `last_*` mix is backtested, if there is one. `remove=<n>` answers 303 with the mix that's left. RK-9: the backtest's `risk` section is shown as a grid of the mix's measures by window and a table of the mix and its assets over one window, `?risk_window=` (`1Y`, `3Y`, `5Y`, `10Y` or `Max`; 1Y when absent or anything else, logged). The window links, the period links, the form and remove's redirect all keep it. See [`labs-ui.md`](labs-ui.md) |

Every POST error (wrong credentials, a duplicate email, a tripped throttle, `auth`/`portfolio`
being unreachable, a CSRF mismatch, or a `portfolio` validation failure) re-renders the form with
a flat, specific message — chapter IV of the brand charter's "no panic, no hype" applies to error
copy as much as to figures. A wrong password and an unknown email deliberately render the same
message, so `web` doesn't reintroduce the enumeration oracle `auth`'s own `passwords.dummy_verify()`
exists to close; no equivalent concern applies to the portfolio routes; see "Key decisions" in [`architecture.md`](architecture.md).

Any path no route matches is a branded 404 page, any other HTTP error or malformed request a
branded page with its own status, and an unhandled exception a branded 500 (UI-12; see
"Feedback and error states" in [`ui-architecture.md`](ui-architecture.md)). None of them is JSON.
